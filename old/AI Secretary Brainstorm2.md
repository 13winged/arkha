## 1. Порядок этапов: S3 навыки перед S4 инструментами — пересмотрено

В прошлый раз поставил навыки раньше инструментов, рассуждая «польза
без агента». Подумал ещё — неправильно.

Навык описывает, **как использовать инструменты**. Навык `files` без
инструмента `read_file` — текст в вакууме. Модель прочитает инструкцию
«используй read_file» и не сможет.

| Порядок | Что видит пользователь | Вердикт |
|---|---|---|
| Навыки → инструменты | «Он ничего не может делать» | плохо |
| Инструменты → навыки | «Вот эти команды работают» | рабочее |

**Решение: поменять местами.** S3 = инструменты, S4 = навыки.

Деталь: чтобы инструкция сработала, модель должна знать про инструмент.
Сначала объявляем 2–3 инструмента в реестре с полными схемами, потом
добавляем навык, объясняющий, как их комбинировать. При трёх инструментах
lean search ещё не нужен.

## 2. Упущено: агент не видит себя

Ни в одном документе нет ответа на вопрос: **как модель понимает, что
может сделать?**

Сейчас: системный промпт + схемы инструментов. Нет инструмента — модель
не знает, что такой существует. Пользователь: «открой Excel и посчитай по
таблице». Без COM-инструмента модель скажет «я не могу».

**Что добавить: реестр возможностей с проверкой доступа.**

| Что | Как |
|---|---|
| Что есть вообще | статический список возможностей |
| Что доступно пользователю | фильтр по профилю и разрешениям |
| Что отключено и почему | с указанием причины |

Модель получает: «Могу работать с файлами, приложениями, окнами, браузером.
Не могу: Excel — нет COM-инструмента на этом профиле.»

Ответ «не могу» с причиной лучше, чем уверенное «сделаю» и провал.
Одновременно решает проблему «половина функции хуже отсутствия».

## 3. Упущено: режим отладки для пользователя

Классическая проблема агентов: агент сделал не то, пользователь не видит
почему, другая формулировка не помогает.

**Что добавить: «почему он это сделал».**

| Вопрос | Ответ в интерфейсе |
|---|---|
| Какие инструменты вызваны | список с аргументами |
| Почему выбран этот | извлечено из рассуждения |
| Что из контекста видел | какие блоки подставлены, откуда |
| Что решил запомнить | список фактов |
| Где уверен, где нет | из ответа модели |

Дёшево: всё это уже есть в receipts и логах, нужен UI. Даёт основной
прирост доверия. Человек, который видит ход решения, не боится
подтвердить.

## 4. Упущено: деградация вместо ожидания

На T1 голосовой цикл 3–6 секунд, на T2 сценарий 30–90 секунд. Пользователь
нажал и ждёт.

| Вопрос | Текущий ответ |
|---|---|
| Показать прогресс | есть индикатор «думаю» |
| Сколько ждать осталось | нет данных |
| Что делать при нехватке времени | нет |

**Что добавить:**

| Ситуация | Поведение |
|---|---|
| T1, сложный запрос | «это займёт до минуты» |
| Превышено время ожидания | предложить: продолжить локально или в облако |
| Задача из 10 шагов на T1 | предложить разбить, выполнить часть |
| Не хватает VRAM | сократить историю, предупредить |

Плюс грубый счётчик: «ответ займёт примерно N секунд» по типу задачи
и профилю. Лучше неизвестности.

## 5. Упущено: журнал как функция

Мы делаем лог для отладки и receipts для безопасности. Обе — инфраструктура.

**Что добавить: «что секретарь делал без меня».**

| Функция | Описание |
|---|---|
| Хронология дня | во сколько открыл файлы, какие страницы смотрел |
| Отчёт по задаче | что сделано, что не получилось |
| Экспорт | в markdown, для отчёта о работе |
| Поиск по истории | «что я просил на прошлой неделе» |

Секретарь работает, когда пользователь спит. Без журнала это чёрный ящик.
С журналом — видимый результат. Это же основа доверия к проактивности.

## 6. Упущено: первое знакомство

Приложение спросит профиль, покажет модель, скачает 5 ГБ. И всё. Пользователь
не понимает, зачем ему эта программа.

**Что добавить: онбординг с тремя сценариями.**

| Сценарий | Что показывает |
|---|---|
| «Найди все PDF на рабочем столе, скажи что в них» | файлы + чтение |
| «Что нового по теме X в интернете» | поиск + страницы |
| «Открой блокнот, напиши список дел на завтра» | приложения + ввод |

Реальные рабочие сценарии, не «hello world». Плюс явный выбор
«работать локально / разрешить облако» в начале, а не через неделю.

## 7. Упущено: навыки отдельно от приложения

Навыки обновляются вместе с приложением. Но навык — это контент, не код.

**Что добавить: пользователь пишет свой навык через UI.**
«Расскажи секретарю, как ты работаешь» — он генерирует навык сам.

Ограничения: не расширяет инструменты, не меняет автономность,
проходит валидацию. Пользовательский навык — инструкция, не привилегия.

## 8. Упущено: почта и календарь как отдельная сложность

COM к Outlook — отдельная история:

| Проблема | Суть |
|---|---|
| Новый Outlook (Web) | COM не работает, только веб-интерфейс |
| Старый Outlook | COM работает, API нестабилен между версиями |
| Exchange / M365 | Аутентификация, токены, refresh |
| IMAP | Проще, но нужен пароль приложения |

**Вывод: не обещать почту в MVP.** Два пути:

| Путь | Что даёт |
|---|---|
| Открыть Outlook + UIA | агент читает окно — уже в S6 |
| IMAP-инструмент | настоящий доступ, чтение без UI |

Для «что там в почте» хватит первого. Честнее сказать пользователю:
«пока читаем окно». Календарь проще — локальный файл или COM.

## 9. Упущено: быстрая модель для фоновых задач

Сейчас одна модель на всё. Задачи разные: веб-суммаризация хочет скорости,
отчёт по 10 документам — длинного контекста, ввод текста — надёжного
tool calling.

**Что добавить: переключение на уменьшенный квант для фоновых задач.**

Сайдкар — отдельный процесс, два экземпляра возможны, но 8 ГБ VRAM
не выдержит одновременно. Значит не два инстанса, а **переключение**:
быстрая модель грузится вместо основной для утренней сводки и коротких
ответов. Потеря полусекунды в фоне незаметна.

На T1–T2 невозможно. Оптимизация, не требование.

## 10. Упущено: Windows-специфика, которые сломаются

Из опыта, типичные грабли:

| Грабля | Последствие |
|---|---|
| Антивирус удаляет бинарь llama.cpp | «модель не грузится», причины нет |
| SmartScreen блокирует установщик | не устанавливается вообще |
| Конфликт с существующим Ollama | не запускается |
| Энергосбережение Windows | модель на GPU, но CPU в 10% |
| Несколько аудиоустройств | микрофон выбирается неверный |
| Права на папку с документами | RAG не индексирует без объяснения |

**Что добавить в S11:**

| Мера | Зачем |
|---|---|
| Исключения SmartScreen | подпись сертификатом, если возможно |
| Проверка антивируса при ошибке запуска | подсказать причину |
| Автоопределение свободного порта | не падать из-за конфликта |
| Предупреждение о балансировке питания | объяснить, почему тормозит |
| Список аудиоустройств в настройках | выбор микрофона вручную |
| Понятная ошибка RAG | «нет прав», а не «indexing failed» |

Часть определения готовности, а не «доделываем в конце».

## 13. Честный взгляд на масштаб

30–37 дней — оценка для одного разработчика, знающего материал.
Поправки:

| Фактор | Влияние |
|---|---|
| UIA на реальных приложениях | +50% к S6. Приложения ломают UIA по-разному |
| Голос на T1 | отключить по профилю или +3 дня |
| Установщик без сюрпризов | +2–3 дня на антивирус и SmartScreen |
| Тестирование на T1 | нужен доступ к чужой машине |

Реалистично: **35–45 дней.** Первая рабочая версия — 10–12 дней (S0–S4).

**Не ждать идеального T1 перед релизом.** Сделать MVP для своей машины
(T3), дать попробовать 2–3 людям с разным железом, потом доделывать
нижние профили. Иначе полгода полировки T1 для одного пользователя вместо
проверки нужности продукта.

видно, работает продукт или нет.
