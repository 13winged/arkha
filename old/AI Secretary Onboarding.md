# AI Secretary — сценарий знакомства

Первый и главный сценарий. Не демонстрация возможностей, а разговор,
в котором пользователь собирает своего агента.

---

## Почему этот сценарий — главный

Он закрывает сразу несколько проблем, которые мы не могли решить иначе.

**Работает на T1.** Знакомство — это разговор и список. Ни одного
вызова инструмента. Значит доступно половине пользователей, включая
владельцев машин без GPU.

**Снимает проблему нехватки данных.** Мы не знали, какой сценарий
важен. Пользователь отвечает на вопрос «что тебе доступно?» — и это
одновременно онбординг, настройка и проверка работы агента.

**Проверяет модель, а не только софт.** Понимает ли модель свои
возможности и границы? Говорит ли «не могу» вместо уверенного
«сделаю»? Это проверка tool calling и инструкций в одном.

**Делает разрешения видимыми с первого дня.** Пользователь не
разбирается в L1/L2/L3. Он видит: «папка Загрузки — да, документы —
нет». Это понятнее абстрактных уровней автономности.

**Даёт расширяемость.** Пользователь возвращается и добавляет
возможности. Агент растёт вместе с задачами, а не с версиями.

---

## Что должно произойти

### Диалог 1. Представление

**Агент:** «Привет. Я секретарь. Работаю на твоём компьютере, всё
локально — никуда ничего не отправляю.»

**Агент:** «Сейчас я умею [перечисляет то, что доступно на этом
профиле]. Не умею [перечисляет то, что отключено, с причиной].»

**Зачем:** пользователь сразу понимает границы. Не узнаёт о них
через неделю, когда что-то не сработало.

### Диалог 2. Инструменты

**Пользователь:** «Какие у тебя есть инструменты?»

**Агент:** перечисляет с пояснением, что каждым можно.

| Инструмент | Что делает | Доступен |
|---|---|---|
| Файлы | читать, искать, создавать | да |
| Приложения | запускать, закрывать | да |
| Окна | видеть открытые, переключаться | да |
| Интернет | искать, читать страницы | да |
| Документы | искать по корпусу PDF/DOCX | нет — корпус не выбран |
| Excel и Word | работать с таблицами | нет — нет COM на этом профиле |
| Почта | читать и отправлять | нет — не подключено |

**Зачем:** «не умею — потому что корпус не выбран» ведёт к действию.
«не умею» без причины — к раздражению.

### Диалог 3. Папки

**Пользователь:** «Какие папки тебе доступны?»

**Агент:** «Пока никаких. Мне нужно разрешение. Какие папки открыть?»

Показывает разумные варианты, найденные на диске:

```
Рабочий стол        — да / нет
Загрузки            — да / нет
Документы           — да / нет
D:\Работа           — да / нет  [выбрать папку]
```

**Пользователь:** «Рабочий стол и Загрузки. Папку с рабочими
документами пока не хочу.»

**Зачем:** выбор из списка быстрее, чем навигация по дереву. И список
подсказывает то, о чём пользователь не подумал бы.

### Диалог 4. Уточнение поведения

**Агент:** «Понял: Рабочий стол и Загрузки. Что мне можно делать с
ними без твоего подтверждения?»

| Уровень | Что означает | Пример |
|---|---|---|
| Только читать | ничего не меняю | найти, прочитать, рассказать |
| Читать и создавать | могу делать новое | составить список дел в новый файл |
| Полный доступ | могу перемещать и удалять | разложить файлы по папкам |

**Зачем:** пользователь не знает про L1/L2/L3. Он знает про «можно
удалять» или «нельзя». Переводим на его язык.

### Диалог 5. Проверка

**Агент:** «Готово. Проверю: на твоём рабочем столе лежат вот эти
файлы... [перечисляет]. Хочешь, чтобы я показал содержимое одного?»

**Пользователь:** «Да, notes.txt»

**Агент:** [читает, пересказывает]

**Зачем:** первое реальное действие с реальным разрешением. Пользователь
видит, что границы работают, до того как доверит что-то важное.

### Диляог 6. Итог

**Агент:** «Итог. Умею: файлы на Рабочем столе и в Загрузках, читаю;
интернет. Создавать файлы могу с твоим подтверждением. Удалять —
не могу без явной команды. Чего хочешь добавить?»

**Зачем:** явный список того, что агент понял. Если не то — правится
сейчас, а не через неделю. И приглашение добавить ещё.

## Что это меняет в архитектуре

### Реестр возможностей

Появляется в S1 как фундамент, а не как доработка.

```json
{
  "id": "files.read",
  "title": "Чтение файлов",
  "description": "Находить и читать текстовые файлы",
  "requires": [],
  "tier": "T1",
  "risk": "none",
  "default_enabled": false,
  "needs_grant": "paths"
}
```

| Поле | Что даёт |
|---|---|
| `tier` | недоступно на слабом железе — агент объясняет почему |
| `risk` | определяет, можно ли без подтверждения |
| `needs_grant` | `paths` — нужно разрешение папок |
| `default_enabled` | что работает без настройки |

Агент получает **читаемый** реестр. Это механизм против галлюцинаций
из Brainstorm2 п.2: модель знает, что существует, что доступно
и почему нет.

### Хранилище разрешений

```json
{
  "paths": ["C:\\Users\\me\\Desktop", "C:\\Users\\me\\Downloads"],
  "capabilities": {
    "files.read":    { "enabled": true,  "mode": "auto" },
    "files.write":   { "enabled": true,  "mode": "confirm" },
    "files.delete":  { "enabled": false, "mode": "never" },
    "web.search":    { "enabled": true,  "mode": "auto" }
  },
  "cloud": false
}
```

| Уровень | Что означает |
|---|---|
| `auto` | без подтверждения |
| `confirm` | с подтверждением |
| `never` | запрещено |

### Настройки как разговор

Разговор знакомства — это не отдельный экран. Это обычный чат,
который в конце сохраняет конфигурацию.

**Почему важно:** настройка через форму и через разговор — два разных
сценария, и второй приятнее. Пользователь не заполняет поля, он
объясняет, что ему нужно. Агент переводит в конфигурацию и
показывает результат для подтверждения.

## Порядок этапов

Знакомство — не S11 как онбординг, а **S3**, сразу после чата.

| Этап | Что | Результат |
|---|---|---|
| S1 | Профиль + реестр возможностей + разрешения | агент знает, что может |
| S2 | Инференс, чат | разговор работает |
| **S3** | **Сценарий знакомства** | **пользователь собрал агента** |
| S4 | Инструменты: файлы, приложения | первые действия |
| S5 | Навыки | инструкции поверх инструментов |

**Знакомство делится на две части:**

| Часть | Когда | Что проверяет |
|---|---|---|
| Разговор без инструментов | S3 | модель понимает свои границы |
| Проверка с чтением файла | S4 | разрешения реально работают |

Диалог 5 (проверка) переносится в S4, когда появятся первые инструменты.
Диалоги 1–4 и 6 остаются в S3.

**Почему S3 до S4:** без реестра возможностей агент не сможет честно
рассказать о себе. Реестр — данные, он не зависит от наличия
инструментов: он описывает то, что *будет* доступно.

---

## Что проверяем на S3

| Проверка | Критерий |
|---|---|
| Агент перечисляет свои инструменты | список совпадает с реестром |
| Агент объясняет недоступное | называет причину, а не просто «нет» |
| Агент принимает выбор папок | сохраняет, применяет на следующем шаге |
| Агент спрашивает про уровни доступа | не навязывает, но и не пропускает |
| Агент перечисляет итог | соответствует фактическому состоянию |
| Повторное открытие | агент помнит, что настроено |

Отдельно: агент не должен предлагать то, чего на профиле нет. И должен
предлагать добавить возможности, если пользователь об этом спросит.

## Открытые вопросы

1. **Одноразовое знакомство или повторяемое?** Агент может периодически
   предлагать добавить возможности. Полезно или навязчиво?
2. **Кто решает дефолты?** Строгие по умолчанию безопаснее, но больше
   вопросов на старте. Можно разделить: файлы только чтение, всё
   остальное выключено.
3. **Можно ли менять настройки через разговор потом?** «Забудь папку
   Загрузки». Если да — конфигурация меняется из любого диалога. Это
   удобно и это новый вектор: инструкция из веб-страницы не должна
   иметь возможности это сделать.
4. **Показать ли код конфигурации?** Для продвинутых пользователей —
   да, возможность посмотреть и поправить. Для остальных — нет.

---

## Связь с навыком

Навык `onboarding` — не инструкция для агента, а сценарий приложения.
Агент получает только список возможностей и текущие разрешения, плюс
общие правила: не предлагай недоступное, объясняй причину, спрашивай
про уровни, подтверждай итог перед сохранением.

Всё остальное — логика приложения: поиск папок для предложения,
сохранение конфигурации, валидация.
