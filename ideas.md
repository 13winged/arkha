## 1. AUV — «Application Use Via»

**Apache-2.0, Rust, 98 звёзд.** Самый интересный репозиторий организации
для нас.

### Что это

> No we are not computer use, it's Application Use Via...
> a unified orchestration layer of OS automation, 0 token cost

Playwright для операционной системы. Не агент — библиотека
GUI-автоматизации, которую вызывает агент.

### Главная идея

Текущий цикл computer-use у всех одинаковый:

```
Agent → screenshot → read image → decide → click → wait → type → verify → повторить
```

Каждая итерация тратит токены на интерпретацию картинки, хотя
последовательность повторяется. AUV предлагает выносить
повторяющиеся операции в код:

| Цикл вызовов инструментов | Скрипт на Rust |
|---|---|
| 8 вызовов: скриншот, прочитать, нажать, ввести, скриншот, проверить | `app.open(); app.wait_for_ready(); app.fill(data); app.verify_submitted()` |
| скриншот → OCR → скролл → OCR → угадать когда остановиться | `region.scan_rows_until_stop()` |
| нажать → скриншот → семантическая проверка → повтор вручную | `retry_until_verified(&mut operation)` |

**Нулевая стоимость рассуждения на повторных прогонах.**

### Почему это важно для нас

Мы это уже отметили как идею из Hermes — «скрипты вызывают инструменты
по RPC». AUV доводит её до production: типизированные операции,
проверяемые результаты, версионированные контракты.

Для секретаря это снимает главную проблему слабого железа:
десятишаговый сценарий на 9B занимает 30–90 секунд. Тот же сценарий
как скомпилированная операция — секунда и ноль токенов.

### Что брать

| Идея | Куда |
|---|---|
| Библиотека типизированных GUI-операций | S8 |
| `verify_submitted()` как часть операции, а не отдельный шаг | S7, усиливает readback |
| `scan_rows_until_stop()` — понятные причины остановки | S7, вместо потолка шагов |
| `retry_until_verified()` — повтор внутри операции | S7 |
| Protobuf/gRPC контракты с версионированием | позже, если появится удалённый доступ |
| Feedback: input path, изменения, артефакты, fallback, результат проверки | S6, `audit.jsonl` |
| «Визуальный курсор не заменяет доставку ввода и семантическую проверку» | правило в документацию |

### Почему не берём целиком

- Матрица возможностей показывает: Windows-драйверы ⏳ (запланировано),
  ghost cursor на Windows ❌, OCR на Windows ✅
- Linux musl не поддерживается
- macOS helper — подписанное приложение, Windows helper требует
  elevated PowerShell и регистрации сервиса LocalSystem
- «Evidence level: one installed lock and unlock gate on one Windows 11 host.
  This is not a general support claim» — их собственная формулировка
  про зрелость Windows-поддержки

**Вывод: идеи берём, код — нет.** Windows-драйвера у них сами
в планах. Писать UIA-слой самим всё равно.

### Что стоит проверить

Их `crates/` и `supported/` — как устроены драйверы и operation crates.
Архитектурно полезно даже если код не переиспользуем.

## 2. plast-mem — память

**MIT, Rust, 74 звезды.** Слой памяти на когнитивных принципах.

### Что это

Self-hosted, один бинарник, нужна только LLM-служба и база ParadeDB.

### Два слоя памяти

| Слой | Что хранит | Механизм |
|---|---|---|
| **Эпизодическая** | «что произошло» — дискретные события с границами | FSRS для затухания |
| **Семантическая** | «что известно» — факты и поведенческие правила | временная валидность, без затухания |

### Сегментация разговора

> Человеческая память сегментирует поток на дискретные эпизоды.

Пласт Мем находит естественные границы: смена темы, временной разрыв,
накопление сообщений. Один вызов LLM разбивает разговор на эпизоды,
у каждого — заголовок, сводка, **уровень неожиданности**.

### Консолидация

Запускается офлайн. При 3+ эпизодах или при «вспышке памяти»
(surprise ≥ 0.85) LLM обрабатывает эпизоды против существующего
знания и выполняет: новое / подкрепление / обновление / инвалидация.

### Забывание

FSRS — планировщик интервального повторения. Эпизоды с высоким
surprise получают буст стабильности и затухают медленнее.

Семантическая память FSRS не использует: факт живёт, пока его
явно не опровергли.

### Извлечение и поиск

| Приём | Что даёт |
|---|---|
| BM25 по сводкам и ключевым словам | лексическое совпадение |
| Векторное сходство через эмбеддинги | семантика |
| **RRF** — Reciprocal Rank Fusion | слияние двух рангов |
| FSRS retrievability как реранкер | затухание учитывается при поиске |

### Почему это интересно нам

Мы в `docs/02` написали: «только то, что модель явно решила запомнить,
иначе качество поиска деградирует за месяцы». Plast Mem решает это
системно: факты консолидируются из эпизодов, невалидные инвалидируются,
затухание моделируется.

**Для секретаря существенно:** пользователь скажет «про РАСу», «я
предпочитаю кратко», «у меня отпуск в июле». Через месяц без системы
консолидации это либо забудется, либо окажется в базе навсегда.

Их FAQ: «Почему не графовая БД?» — «удобство self-hosting важнее».
Мы на sqlite-vec по той же причине.

### Что брать

| Идея | Куда | Приоритет |
|---|---|---|
| Эпизодическая + семантическая память как два слоя | S11 | высокий |
| Сегментация разговора на эпизоды | S11 | средний |
| Surprise level при извлечении факта | S11 | средний |
| RRF для слияния BM25 и векторного поиска | S10, S11 | средний |
| FSRS-затухание для эпизодов | S11 | низкий |
| Консолидация: новое / подкрепление / обновление / инвалидация | S11 | средний |
| Восемь типов фактов: личность, предпочтение, интерес, характер, отношения, опыт, цель, руководство | S11 | средний |

### Что не берём

| Что | Почему |
|---|---|
| ParadeDB | Отдельный сервер. Мы на sqlite-vec |
| FSRS целиком | Требует цикла повторения. Секретарь не Quizlet |
| LLM-сегментация каждого батча | Дорого на 9B. Только на консолидации |
| Их «designed for Cyber Waifu» | Другая задача, но архитектура переносится |

### Статус проекта

> Мы ещё не выпустили 0.1.0, потому что основная функциональность
> не завершена.

Честно. Идеи смотреть можно, код брать рано.

### Что стоит проверить

`docs/ARCHITECTURE.md` и `examples/haru`. HARU — похоже на
полноценный пример агента, а не только библиотека.

## 3. ortts — локальный TTS

**MIT, Rust, 13 звёзд.** OpenAI-совместимый сервер синтеза речи
на ONNX Runtime.

### Что это

`POST /v1/audio/speech` — тот же интерфейс, что у OpenAI.

| Бэкенд | Что |
|---|---|
| Kokoro | наш текущий выбор |
| Chatterbox Multilingual | мультиязычный |
| Qwen3-TTS 0.6B Base | с референсным аудио, языки zh/en/ja |

Одна точка входа, несколько бэкендов.

### Почему интересно нам

Мы в `docs/02` спроектировали интерфейс `TTSProvider` с локальной
и облачными реализациями. Ortts — это **готовый локальный TTS-сервер
с тем же интерфейсом, что облако**.

Это значит: если бы мы держали TTS как сервис, то
переключение «локальный Kokoro → облачный ElevenLabs» было бы
сменой URL, а не кода.

### Что брать

| Идея | Куда |
|---|---|
| TTS как отдельный сервис с OpenAI-совместимым API | S9 |
| Единая точка входа, бэкенды как драйверы | S9 |
| Chatterbox Multilingual как альтернатива Kokoro для русского | S9, тест |
| Встроенная OpenAPI-документация | S13 |

### Спорный момент

Мы сознательно отказались от Docker и лишних процессов. TTS-сервер —
это ещё один процесс плюс порт.

**Компромисс:** встраивать TTS в процесс приложения (Kokoro через
ONNX Runtime напрямую), но держать интерфейс `TTSProvider` совместимым
с OpenAI — чтобы облачный бэкенд подключался сменой base URL.

### Что не берём

| Что | Почему |
|---|---|
| Qwen3-TTS Base | Только zh/en/ja. Русского нет |
| Docker-образ | Мы без Docker |
| Rust-сервер как отдельный процесс | Лишний процесс на 16 ГБ |

## 4. vishot — проверка через скриншоты

**MIT.** Vitest + скриншоты: «если можешь playwright, то можешь и
скриншот». Заявлено применение: продуктовые мокапы, документация,
**agent verify**.

### Зачем нам

У нас нет способа проверить, что интерфейс работает. Скриншот-тесты
позволяют проверять визуальное состояние приложения.

Но: это про тестирование нашего UI, а не про продукт. Низкий приоритет.

### Что брать

Идея «визуальная проверка как часть агентного цикла» — уже есть у
нас в виде readback и скриншотов после действий. Совпадает.

## 5. velin — промпты как компоненты

**MIT.** Промпт-оркестрация через Vue/React-компоненты. Совместим
с любым Node-рантаймом.

### Зачем нам

У нас системный промпт собирается из кусков: реестр возможностей,
текущие разрешения, активные навыки, история, RAG-выборка. Сейчас это
склейка строк.

Velin даёт компонентную модель: промпт — это дерево компонентов
с условиями рендеринга и лимитами бюджета.

### Что брать

| Идея | Куда |
|---|---|
| Промпт как дерево компонентов, не склейка строк | S4, S5 |
| Условный рендеринг: блок появляется только если есть данные | S5 |
| Бюджет промпта на компонент | S5 |

### Спорный момент

Мы на React, а Velin — Vue-компоненты. Прямое использование потребует
порта. Идея переносится, код — нет.

## 6. xsai — минимальный AI SDK

**MIT, 661 звезда.** Поддерживает 30+ провайдеров, включая
vLLM, SGLang, Ollama, OpenAI-compatible.

### Что берём

Идея: провайдер — это дескриптор, а не код. Смена провайдера =
смена дескриптора. У нас это в правилах уже есть.

Код не берём: мы обращаемся к llama-server напрямую по
OpenAI-совместимому API, один бэкенд, обёртка не нужна.

## 7. unspeech — отклонён по лицензии

**AGPL-3.0.** Прокси для TTS с OpenAI-совместимым API.

AGPL — сетевая копилефта. Встраивание в коммерческий продукт
потребует открытия исходников подключённой части.

Мы сознательно избегали AGPL: цель — «максимально доступный софт,
почти любой юзер мог бы пользоваться». AGPL-компонент в
распространяемом приложении — это либо юридический риск, либо
обязательное открытие кода.

**Решение: не использовать.** Организация в тех же материалах
рекомендует его как альтернативу LiteLLM для аудио. Мы делаем
свой слой выбора провайдера, лицензия чистая.

## Общая картина

### Что организация сделала правильно

| Решение | Почему это важно |
|---|---|
| Вынесла подсистемы в отдельные репозитории | `plast-mem`, `ortts`, `auv` переиспользуемы независимо от AIRI |
| Разделяет Rust и TypeScript по задаче | Rust для систем (память, GUI, TTS), TS для фронта |
| Пишет границы зрелости честно | «Evidence level: one Windows 11 host. Not a general support claim» |
| Документирует отрицательные результаты | Исходные эксперименты не удаляются |
| Малые проекты с MIT/Apache | Можно взять код, а не идею |

### Чего у них нет

**Секретной работы.** Ни одного репозитория про:
- многошаговые планы с подтверждениями
- права доступа по уровням
- readback как обязательный шаг
- prompt injection как граница доверия
- профили железа с автоподбором рецепта

Всё это мы спроектировали сами. У них — инфраструктура, у нас —
продуктовая логика. Хорошее разделение.

## Вывод

Четыре репозитория из 55 дают применимое. Остальное — либо
другая задача, либо не та платформа, либо AGPL.

**Самая ценная находка — AUV.** Идея «Playwright для ОС» решает
главную проблему слабого железа: повторяющиеся GUI-сценарии
не должны стоить токенов. Мы это отметили ещё на этапе брейншторма,
но без production-решения.

**Вторая — plast-mem.** Наша память сейчас примитивная: «явные
предпочтения в sqlite-vec». Двухслойная модель с консолидацией
и инвалидацией — это то, что нужно, чтобы секретарь оставался
полезным через месяцы, а не через неделю.

**Третья — ortts.** Подтверждает архитектурное решение: TTS
за единым OpenAI-совместимым интерфейсом, локальный бэкенд.

**Код не берём.** Windows-поддержка AUV ещё в планах, plast-mem
не выпустил 0.1.0, ortts — это сервер, а мы сознательно идём
без лишних процессов. Берём идеи и проверяем в своих условиях.
