# 11. Журнал находок

Записи по мере работы. Каждая — либо поломка в коде, либо расхождение
плана с измерением. Хронологично.

## 2026-10-11. Приложение не находит llama-server

Скриншот запущенного приложения, вкладка «модель», после нажатия
«Запустить модель»:

```
ни один рецепт не запустился: 9B Q5_K_M + q4_0 — не найден
llama-server.exe: data/bin\llama\llama-server.exe. Установите
llama.cpp b11557 в папку bin
```

При этом профиль определился верно: **T3**, в подвале видно
«профиль: T3». Определение железа работает.

### Что тут три разные проблемы

**Первая: путь считается от текущего каталога, а не от exe.**

`bin_dir()` проверяет `exe_dir/llama`, потом переменную `ARSHA_BIN_DIR`,
и только потом откатывается на относительный `data/bin`. Относительный
путь разрешается от того каталога, из которого запустили, а exe лежит в
`target/release`. Запуск из корня проекта работает, запуск из папки
исполняемого файла — нет.

Это не «не установлено», это ошибка разрешения пути. Для пользователя
разница не видна: сообщение говорит «установите llama.cpp», хотя он
установлен и лежит в проекте.

Как надо: искать `bin` относительно exe, на несколько уровней вверх,
и в установленной сборке рядом с exe. Молчаливый откат на относительный
путь убрать — лучше честная ошибка «не найдено, искали здесь-то».

**Вторая: на этой машине нет модели для T3.**

T3 по рецептам требует `Qwen3.5-9B-Q5_K_M.gguf`, ~6.5 ГБ. На dev-машине
лежит только Q4_K_M, 5.4 ГБ. Второй рецепт T3, экспериментальный
27B UD-IQ2_XXS, тоже отсутствует.

Это ожидаемо: рецепты T3 и T4 не замерялись, о чём записано в
[10-замеры](10-замеры.md). Но сообщение об ошибке сейчас вводит в
заблуждение: оно про llama-server, а на самом деле первым делом не
найдена модель.

**Третья: порядок проверок перевёрнут.**

Сейчас сначала проверяется бинарник, потом файл модели. Пользователю
показывают первую ошибку, даже если проблем несколько. Правильнее
собирать все причины и показывать списком: «нет модели для T3», «нет
llama.cpp».

### Что из этого следует

| Что | Статус |
|---|---|
| Определение профиля | работает, T3 определён верно |
| Разрешение пути к бинарнику | сломано, правится в `model_manager.rs` |
| Проверка наличия модели | молчаливый откат на следующий рецепт |
| Скачивание модели | **не реализовано**, и это главное препятствие |
| Q5_K_M для T3 | не замерялся |

Главное здесь то, что отсутствует **загрузчик модели**. Он и был
запланирован на S2, пункт 3: скачать с Hugging Face, проверяя digest
каждого файла. Без него пользователь с чистой машиной не сможет
начать работу: приложение не умеет самостоятельно получить то, что ему
нужно, и объясняет это одной строкой.

Раз Т3 на dev-машине, а гейт S2 закрывался на T2-рецепте с тем же
файлом модели, стоит проверить: помещается ли Q4_K_M на T3, и каким
контекстом. Замер честнее, чем предположение.

## 2026-10-11. Можно ли использовать LM Studio вместо своего загрузчика

Проверено по документации и на живой машине: `lms` уже установлен,
`~/.lmstudio/bin/lms.exe`, версия CLI из документации совпадает.

### Что такое «загрузчик» из плана

Это не готовая библиотека и не чужой компонент. Это наш код, примерно
250 строк в `model_manager.rs`:

| Что | Как |
|---|---|
| Скачать файл | GET на `huggingface.co/{repo}/resolve/main/{файл}` |
| Проверить подлинность | SHA-256 из `huggingface.co/api/models/{repo}/tree/main`, сверка после загрузки |
| Докачать после обрыва | HTTP Range, с места остановки |
| Показать прогресс | события Tauri по мере чтения потока |
| Проверить комплектность | размер, наличие всех файлов репозитория |

Проверка digest — не паранойя, а требование правила 15: файл на 5–6 ГБ,
пришедший недоверенным каналом, либо повреждён, либо подменён. Без
сверки мы не знаем, что запускаем.

*Основание изменилось, сама проверка — нет.* Раньше это было
следствием запрета на непроверенную лицензию. Запрет снят 12 октября
2026, но сверка осталась обязательной по другой причине: она защищает
от подмены файла, а не от нарушения авторских прав. Снятие правила 15
на целостность не влияет.

### Что даёт LM Studio

| Возможность | Есть |
|---|---|
| `lms get` — скачать модель | да |
| `lms load --gpu=max --context-length=N` | да |
| `lms server start` — OpenAI-совместимый сервер | да |
| `llmster` — демон без GUI | да |
| REST API загрузки и статуса загрузки | да |

Выглядит как готовый ответ на наш вопрос. Но проверка `lms load --help`
на этой машине показывает три блокера.

### Блокер 1: нет управления KV-кэшем

Полный список флагов `lms load`:

```
--gpu <offload-ratio>   -c, --context-length   --parallel   --ttl
--speculative-draft-*   --identifier   --estimate-only   -y
```

Ни `-ctk`, ни `-ctv`, ни кванта модели. **Тип KV-кэша не задаётся.**

Для нас это не мелочь. Рецепт в проекте — это квант + KV-кэш + контекст,
и S2 только что доказал, что выбор KV не теория, а измерение: `q4_0`
дал 65.85 tok/s против 65.35 у `q8_0`, оба помещаются в 8 ГБ. Через
`lms load` мы получим то, что LM Studio решил сам, и не сможем ни
воспроизвести наш замер, ни проверить чужой.

`--auto` «choose context length and model placement based on available
resources» существует, но в документации указано, что доступен только
с Bionic, и он всё равно не про KV.

### Блокер 2: нет подтверждения полного размещения

Наша проверка «все слои на GPU» читает строку `offloaded X/Y layers to
GPU` из лога llama.cpp. `lms load` отдаёт результат через API и такой
строки не даёт.

Правило «если модель не помещается — менять квант, а не оставлять
часть в RAM» держится на этом измерении. Offload стоит 6–8 раз по
скорости, это разница между рабочим приложением и бесполезным. Отдавать
такую проверку наружу, не проверив её, — значит вернуть пользователю
тихий провал вместо понятной ошибки.

### Блокер 3: лицензия `llmster` неясна

`lms` — MIT, проверено в `LICENSE` репозитория
`lmstudio-ai/lms`, копия 2024 года LM Studio. Это CLI.

`llmster` — ядро LM Studio, упакованное как отдельный демон. Репозиторий
ядра открытым не является: `lms` в нём только обвязка. Устанавливается
скриптом `irm https://lmstudio.ai/install.ps1 | iex`.

Правило 15: не проверена — не используем, неясна — не используем.
Здесь именно «неясна».

Даже если бы лицензия оказалась пермиссивной, остаётся требование
установки: либо LM Studio на машине пользователя, либо запуск скрипта
из PowerShell. Обещание проекта — один установщик, без терминала,
без перезагрузок. Этот путь его ломает.

### Решение

**Пишем свой загрузчик.** Он небольшой, мы контролируем и HTTP-запрос,
и проверку digest, и прогресс. Ни одной лицензионной неопределённости,
ни одного лишнего шага установки.

| Вариант | Вердикт |
|---|---|
| Свой загрузчик поверх `reqwest` | берём |
| `lms get` в продукте | нет: требует LM Studio у пользователя |
| `llmster` как рантайм | нет: лицензия неясна и теряется контроль над KV |
| LM Studio как запасной вариант | возможно позже, если появится пользователь, которому проще с готовым приложением |

`lms get` остаётся полезным **для разработки**: он умеет качать модели с
Hub быстро и без нашего кода. На dev-машине это способ получить
`Q5_K_M` для замера T3, не тратя время на собственную реализацию.
В продукт это не идёт.

### Что изменилось в плане

Ничего не отменяется, но пункт обоснован измерением, а не ссылкой на
документацию. Отдельно появился подпункт: загрузчик обязан уметь
докачивать с места обрыва. Скачивание 6 ГБ по домашнему интернету
рвётся, и требовать от пользователя начинать заново — значит отказаться
от установки на середине.

## 2026-10-11. Разбор статьи «Локальный чатбот без ограничений»

Статья на Habr от 27 июня 2025, гайд по LM Studio для новичков.
Как источник по архитектуре слабая: это обзор для пользователя, а не
инженерная документация. Но три вещи в ней бьют по нашим решениям,
и одну из них мы не заметили сами.

### 1. В наших рецептах нет параметров выборки

Стария перечисляет то, чем реально управляют при локальном запуске:
`temperature`, `top_p`, `top_k`, `repeat_penalty`, `max_tokens`.

В `data/recipes.json` у нас есть только квант, KV-кэш и контекст.
Параметров выборки нет вообще, и они неявно берутся из шаблона модели.

Для секретаря это не мелочь. При температуре 0.8–1.2 модель
«фантазирует» — а секретарь выполняет поручения. В худшем случае
она выдумает имя файла, которого нет, и объявит задачу выполненной.

Добавлено в рецепты: `temperature` 0.3, `top_p` 0.9, `top_k` 40,
`repeat_penalty` 1.1. Значения — по рекомендациям статьи, перенесённым
в наш случай, а не скопированным: секретарю нужна точность, а не
разнообразие формулировок.

### 2. Статья утверждает, что ниже 16 ГБ RAM безнадёжно

Цитата: «без минимум 16GB RAM это дело заранее безнадёжное».
Минимальный порог у автора — 16 ГБ, желательно 32.

**У нас T1 определён как 8 ГБ RAM с встройкой или 3060 4 ГБ.**
Это прямое противоречие нашей целевой аудитории.

Что из этого следует: либо T1 нереалистичен и мы строим продукт для
машин, которых половина пользователей не имеет, либо статья права и
надо поднимать нижнюю границу.

Развилка честная и её надо разрешить замером на реальной машине с 8 ГБ,
а не рассуждением. Пока помечена как открытый вопрос, см.
[12-план-работ](12-план-работ.md).

Для контекста: тот же автор считает «золотой серединой» 16–22b на
потребительском железе, и это согласуется с нашими T2–T3. Спорный
только нижний край.

### 3. Предупреждение про лицензию Qwen оказалось неприменимым

Статья пишет: Qwen распространяется под Apache-2.0, «однако некоторые
весовые категории (особенно крупных MoE-моделей) могут иметь
ограничения при использовании в Китае и в облачных продуктах».

Проверено по первичному источнику:

| Что | Значение |
|---|---|
| Репозиторий | `Qwen/Qwen3.5-9B` |
| Лицензия в метаданных | `apache-2.0` |
| Файл LICENSE | Apache-2.0 без изменений и дополнений |
| Владелец | Copyright 2026 Alibaba Cloud |
| Gated | нет |

Ограничений нет. Предупреждение автора относится к крупным MoE, а не к
нашей 9B. Запись в таблице лицензий остаётся, теперь она подтверждена
первичным источником, а не пересказом.

Репозиторий `Qwen/Qwen3.5-9B-GGUF` отдаёт 401 без авторизации — файла
модели в официальном GGUF-репозитории по такому имени нет, а модель на
dev-машине получена сторонним путём. Это отдельный вопрос к
загрузчику: **откуда брать файл и как проверить, что это именно он.**

### 4. Статья рекомендует uncensored-модели, мы — нет

В списке моделей для «отсутствия цензуры» автор приводит MythoMax,
dolphin, и отдельно объясняет отсутствие фильтров как преимущество
локального запуска.

Мы идём против этого, и это решение осознанное, зафиксированное в
[02-архитектура](02-архитектура.md): снятие цензуры смещает границу
для разрушительных действий тоже. Модель, которая отказывает на
«найди PDF», ломает продукт; модель, которая отказывает на «удали
этот файл», — это правильное поведение, которое подстраховывает слой
инструментов.

Отказ обрабатывается в инструментах, а не снятием ограничений модели.
Статья с этим не согласна, и это расхождение стоит держать в голове:
часть нашей целевой аудитории может прийти именно за «нет фильтров»
и уйти разочарованной.

## 2026-10-11. HF-Downloader и документация по скачиванию

Пользователь прислал `pramjana/HF-Downloader` из r/LocalLLaMA и
ссылку на документацию Hugging Face. Первое оказалось полезным как
проверка наших требований, второе — как источник проблемы, которую мы
не учли.

### HF-Downloader пригоден как источник идей, но не кода

Apache-2.0, всё чисто с лицензией. Но это PySide6-приложение на Python
с поиском по моделям и таблицей файлов, а не библиотека. Встроить его
в Tauri нельзя: потребовался бы Python и Qt в поставке, то есть ровно
то, от чего мы отказались, отказываясь от WSL2 и Docker.

Три звезды, пять коммитов, описание отсутствует. Как фундамент — нет.

Список его возможностей совпал с нашим и оказался правильным: поиск,
просмотр файлов с размерами, выбор файлов или всего репозитория,
докачка, проверка размера, параллельные HEAD-запросы для быстрого
определения размеров. Ничего нового, но подтверждает, что набор
требований не избыточный.

### Xet-протокол нам не нужен

Документация говорит, что модели на Hub хранятся в Xet и для скорости
предлагает `hf_xet` с адаптивной параллельностью до 64 потоков.

Проверено живым запросом — Xet не нужен:

```
GET https://huggingface.co/{repo}/resolve/main/{файл}
  → 302 Location: https://us.aws.cdn.hf.co/xet-bridge-us/...
  → Accept-Ranges: bytes
  → X-Linked-ETag: "d784ce9eda1a5a7b51e8f705a9e6310844bf4f173654d115823c775fdea56d43"
```

Обычный GET отдаёт целый файл. `hf_xet` — решение Hugging Face для
массовых загрузок и CI, нам оно не требуется и тащить его не нужно.

### Что мы не учли: прокси и файрвол

Файл отдаётся не с `huggingface.co`, а с CDN после переадресации.
В корпоративных сетях эти домены часто не разрешены, и разрешать
только `huggingface.co` недостаточно.

Hugging Face публикует машинно-читаемый список нужных хостов:
`https://huggingface.co/.well-known/meta.json`, и отдельно предупреждает,
что он меняется при добавлении новых хранилищ.

Для продукта с российской аудиторией это не теория. Поведение при
неудаче должно называть точную причину и показывать список доменов,
а не сообщать «загрузка не удалась».

**Российские зеркала как опция** — пока гипотеза. Нужны реальные
цифры отказов, а они появятся только после первых установок.

### Побочная находка: происхождение модели подтверждено

Файл `Qwen3.5-9B-Q4_K_M.gguf` на dev-машине побывал неизвестного
происхождения. Сверили:

| | Размер | SHA-256 |
|---|---|---|
| Локальный файл | 5 680 522 464 | `03b74727a860a563…` |
| `unsloth/Qwen3.5-9B-GGUF` | 5 680 522 464 | `03b74727a860a563…` |
| `bartowski/Qwen_Qwen3.5-9B-GGUF` | 6 169 341 984 | `d784ce9eda1a5a7b…` |
| `lmstudio-community/Qwen3.5-9B-GGUF` | 5 627 044 256 | `cd76ec205963b3b3…` |

Совпадение с unsloth побайтовое. Один и тот же квант от разных авторов
весит по-разному: 5.29 ГиБ против 5.75 ГиБ. Это разные прогоны
квантования, и **выбор репозитория — часть рецепта**, а не мелочь.

Прописано в `data/recipes.json` с указанием репозитория, точных имён
файлов и сводок.

## 2026-10-11. Загрузчик LM Studio: подбор под устройство

Скриншоты окна выбора моделей LM Studio 0.4.25. Смотрим, как устроен
подбор, и что из этого стоит взять.

### Что делает LM Studio

| Элемент | Что показывает |
|---|---|
| Фильтр | «Only include Staff Picks that can fit on this device» |
| Подпись под фильтром | «Based on an estimated model capacity of 32.96 GB» |
| Сортировка | Best Match, Most Likes, Most Downloads, Recently Updated |
| Карточка модели | параметры, архитектура, формат, способности: Vision, Tool Use, Reasoning |
| Выбор файла | список квантов с размером каждого |
| Бейдж | **Partial GPU Offload Possible** |

### Главное наблюдение: их «влезает» — это не наше «влезает»

**32.96 ГБ — это порядок размера оперативной памяти, а не видеопамяти.**
Видеопамять на этой машине 8123 МиБ, то есть примерно вчетверо меньше.

Отсюда и бейдж: для `Qwen3.8 27B Q4_K_M` весом 17.74 ГБ LM Studio
предлагает скачать, помечая «частичная выгрузка на GPU возможна».

**Это ровно тот провал, который наш план запрещает.** Offload стоит
6–8 раз по скорости: 3.8–5.5 tok/s против 31 на том же железе.
LM Studio оформляет это как обычную возможность, значком рядом с
размером файла.

Значит, «фильтр под устройство» у них отвечает на вопрос «влезет ли
в оперативную память», а не «влезет ли на видеокарту целиком». Для
их сценария это разумно: они показывают, что модель запустится, и
пользователь сам решает, готов ли он ждать.

Для секретаря, которому нужен голос и клики по окнам, это неприемлемо.
Сценарий на 10 шагов вместо секунд превращается в 30–90 секунд, а
наш собственный замер в S2 показал 65.85 tok/s на полном размещении.

### Что стоит взять

Пользователь прав: подбор должен быть **и автоматическим, и свободным**.
Ограничивать пользователя списком из пяти профилей неправильно. Но
взять надо не фильтр, а форму.

| Элемент LM Studio | Берём | Как отличаемся |
|---|---|---|
| Сортировка Best Match / Downloads / Updated | да | плюс «по профилю» |
| Карточка с параметрами и способностями | да | добавляем честные цифры замера |
| Выбор любого кванта из списка | да | показываем, что помещается, а что нет |
| Бейдж частичного размещения | **нет, заменяем** | не бейдж, а предупреждение с цифрами |
| Фильтр «влезет по RAM+VRAM» | **нет** | считаем только по видеопамяти |
| Поиск по любой модели на Hub | да | это и есть снятие ограничения |

**Правило вместо фильтра.** Пользователю показывается вердикт по любой
модели:

| Вердикт | Условие | Что показываем |
|---|---|---|
| помещается | все слои на GPU, есть запас под KV | «73% видеопамяти, 65 tok/s» |
| впритык | помещается без запаса | «помещается, но без запаса на рост контекста» |
| частично | не влезает, но запустится | «**будет в 6–8 раз медленнее**, 4 tok/s» |
| не помещается | не влезает даже в RAM | «не запустится» |

Запрещать ничего нельзя: пользователь может взять то, что считает
нужным. Но предупреждение обязано содержать цифры, а не значок.
Решение пользователя остаётся за ним, цена известна заранее.

**Наши рецепты при этом не белый список.** Это рекомендации с
замеренными числами, а кв��лификация разрешённого. Человек с 4090
должен иметь право поставить 27B и получить то, что мы не смогли
замерить.

### Второе наблюдение: способности модели как фильтр

В карточке Qwen3.8 27B явно помечены Vision, Tool Use, Reasoning.
Это полезнее, чем одна строка «27B»: агенту нужно знать не только
размер, но и может ли модель вызывать инструменты.

Наш реестр возможностей S3 должен опираться на это: возможность
«скриншот и понимание картинки» требует модели с Vision, а не
просто 24 ГБ видеопамяти. Планируем T4+ под vision, но пока это
наше допущение, а не проверенное свойство файла.

## 2026-10-11. Jev и разбор System One

Статья от 23 сентября 2026 про модель Jev от TypeSafe AI. Сама модель
для нас непригодна, статья полезна тремя вещами.

### Почему Jev нам не подходит

| Причина | Значение |
|---|---|
| Формат | возвращает распределения по вариантам, а не текст |
| Доступ | облачный API, $0.042 за миллион входных токенов |
| Зрелость | выпущена 15 сентября 2026, независимых оценок мало |
| Прозрачность | архитектура не раскрыта |

Это нарушает базовые ограничения проекта: всё локально, облако
выключено. LM Studio показывает Jev-совместимые эндпоинты, то есть
работает через их сервер, а не у нас на машине.

### Что стоит взять из статьи

**1. «Тирания KV-кэша» — наш замер это подтверждает независимо.**

Автор утверждает: кодовые агенты держат один гигантский контекст с
одной моделью не потому, что это хороший дизайн, а потому что
экономика кэша наказывает альтернативы. Маленькая модель не имеет
уже сформированного кэша большой, и маршрутизация на неё в какой-то
момент дороже, чем продолжить спрашивать ту же дорогую.

Наш замер в S2 сказал то же самое, но проще: **24 000 токенов
разбираются 10.9 секунды**, а 58 токенов — 0.27 секунды. Чем длиннее
история, тем дороже каждый новый шаг.

Два независимых источника, один вывод. Это уже не гипотеза, а
принятое ограничение: переиспользование кэша промпта обязательно,
а не «было бы неплохо».

**2. Тест на устойчивость, который стоит перенять.**

Автор отдельно различает детерминизм и робастность и проверяет второе
конкретно: добавляет к формулировке UUID или nonce и замеряет, не
поплыл ли ответ.

> «Customer wants a refund» и «Customer wants a refund. request_id=4a92f1»
> должны давать одно и то же решение.

Это дешёвый тест, который ловит то, чего не ловит обычная точность:
модель, зацепившаяся за конкретные слова, а не за смысл. У нас
аналогичная проблема с безопасностью: агент не должен менять решение
из-за идентификатора файла в сообщении.

Добавляем в quality gate S2 как отдельную проверку, а не как
пересказ общей метрики.

**3. Декомпозиция и «дешёвый слой вокруг дорогой модели».**

Три мысли совпали с нашими решениями, что ценно как проверка:

| Их формулировка | Наше |
|---|---|
| Не просить модель решить большую задачу, если можно разбить на малые решения | операции вместо цепочки вызовов инструментов |
| Большой системный промпт как глобальная переменная — плохая практика | промпт как дерево блоков с бюджетом |
| Дёшевые проверки вокруг дорогих вызовов, как runtime assertions | readback после каждого действия |

То есть наши решения не уникальны, они стандартны для агентных
систем. Это не плохо, это подтверждение: мы не изобретаем, а следуем
работающему подходу.

Что добавилось: **каскады моделей.** Если маленькая модель уверена,
дорогую звать незачем. У нас есть зачаток этого в bootstrap-режиме
(4B сразу, большая в фоне), но настоящий каскад появится вместе с
оценкой уверенности. Отложено.

## 2026-10-11. Гейт, который проходит, ничего не проверив

Обнаружилось случайно: файл `Qwen3.5-9B-Q4_K_M.gguf` пропал с dev-машины,
и прогон гейта T2 выдал `3 passed ... finished in 0.00s`.

Ноль секунд — это не «быстро», это «ничего не запускалось». Тест
увидел, что файла нет, напечатал `ПРОПУЩЕНО` и вернулся. Rust считает
это успехом.

Опасность не в самом пропуске, а в его виде. Строка `test result: ok`
рядом с `3 passed` выглядит как подтверждение. Кто читает вывод, тот
видит зелёное, а на самом деле проверка молча выпала из процесса.

Почему так вышло: гейт сначала писался для одной машины, где модель
всегда есть. Обработка отсутствия файла появилась позже и была сделана
как мягкий выход — обычный приём, когда тест ещё не стал опорным.
Но гейт по определению опорный: он либо проверил, либо нет.

Исправлено: `require_model()` падает, если файла нет. Сознательно
пропустить можно только явным `ARSHA_ALLOW_SKIP=1`, и тогда это
видно в выводе.

| Ситуация | Было | Стало |
|---|---|---|
| Модель на диске | 3 passed | 3 passed |
| Модели нет | 3 passed за 0.00 сек | **FAILED**, паника с указанием пути |
| Модели нет и `ARSHA_ALLOW_SKIP=1` | 3 passed | 3 passed и `ПРОПУЩЕНО` |

Общее правило, которое из этого следует: **у гейта не должно быть тихого
успеха**. Любой исход, кроме «проверил и прошло», обязан быть заметен.
Мягкий пропуск хорош для юнит-теста; у гейта он равносилен
отсутствию гейта.

## 2026-10-11. Загрузчик блокировался на полном `.part` — 416

Возвращали T2-модель, скачалось 5 680 522 464 байта — ровно полный файл.
Следующий запуск упал за 1.08 секунды:

```
сервер .../Qwen3.5-9B-Q4_K_M.gguf ответил 416 Range Not Satisfiable
```

### Что произошло

Сеть оборвала соединение уже после того, как последний байт записался,
но до переименования `.part` в конечный файл. Состояние оказалось
тупиковым:

- `.part` полного размера,
- загрузчик шлёт `Range: bytes=5680522464-` — запрос за пределами файла,
- сервер справедливо отвечает 416,
- файл удалить — значит качать 5.3 ГиБ заново.

Пользователь оказывался заблокирован: продолжить нельзя, и повторить
нельзя без ручного удаления файла.

### Причина

```rust
if already > 0 {
    req = req.header("Range", format!("bytes={already}-"));
}
```

Ветки «файл уже полный» не было. Размер сверялся только с «больше, чем
нужно» (тогда `.part` удаляется), но не с «ровно столько, сколько нужно».

### Исправление

Полный файл идёт на сверку, сеть не трогается вовсе:

```rust
if already == file.size {
    return finish(&part_path, &final_path, &file, &mut on_progress);
}
```

Сверка и переименование вынесены в `finish()`, потому что нужны в двух
местах: после только что завершённой записи и в этом случае.

### Как тест ловит именно это

Тест без сети и без гигабайтов: `.part` на 2048 байт, у файла сводка
из 64 нулей. Различаются два исхода — «сводка не совпала» (пошла
правильная ветка) и «416» (полез в сеть).

Первая версия теста была пустой: сводка пустая, а отказ по пустой
сводке стоит в самом начале функции, до сетевого кода. Такой тест был
зелёным и со старым багом. Полезно помнить: тест, который не может
упасть, проверяет не то, что думаешь.

Проверено в обе стороны: на старом коде тест падает, на исправленном
проходит. Одно это уже стоило больше, чем тест.

### Общее правило

**Обрыв связи не гарантирует, что файл неполон.** Запись и сверка —
разные шаги, и между ними есть окно. Любой код, который после обрыва
собирается продолжить, обязан различать «не дописано» и «дописано
всё, но не проверено». Иначе восстановление превращается в тупик.
